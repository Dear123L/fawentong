# 法问通 · 多领域法律 RAG 问答后端

> 基于多智能体状态图的多领域法律问答服务：4 节点外层编排 + 4 节点内层检索子图，
> 检索走 BM25 与向量双路召回经加权 RRF 融合，记忆层用 Redis 做短期滑窗与跨会话用户画像。

一个面向中国大陆多领域法律场景的问答后端，覆盖 12 个法域、2186 条法规。用户用口语化提问
（如"100万逾期30天违约金多少"），系统判定问题是否在服务范围内，检索法规库拿到条款依据，
按需触发违约金/利息计算（以违约金计算为典型示例，实际覆盖婚姻继承、劳动社保、借贷、
建设工程、运输、债权转让等场景），

**覆盖范围（12 个法域 / 2186 条法规）**：

| 法域 | 主要内容 |
|---|---|
| 民法典 | 合同编、婚姻家庭编、继承编、物权编、人格权编、侵权责任编 |
| 民事诉讼法 | 管辖、证据、审判程序、执行 |
| 劳动法 / 劳动合同法 | 劳动关系、试用期、违法解除、经济补偿 |
| 社会保险法 | 用人单位缴费义务、滞纳金 |
| 合同编通则司法解释 | 违约金调整、合同效力、履行规则 |
| 诉讼费用交纳办法 | 案件受理费、申请费标准 |
| 劳动争议司法解释（一）（二） | 仲裁与诉讼衔接、竞业限制 |
| 住房租赁条例 | 出租方义务、押金、租金 |
| 劳动保障监察条例 | 用人单位违法责任与处罚 |
| 民间借贷规定 | 利率上限、逾期利息、违约金合计上限 |

范围外（商标 / 专利 / 著作权 / 税务 / 公司股东 / 消费者权益）会直接拒答并说明边界。

**典型示例**：问"100万逾期30天违约金多少"会检索《民法典》第585条等依据，
并按日万分之五（年化上限 4×LPR = 13.8%）算出 15000 元；而"离婚怎么判""工伤怎么赔"
"试用期违法吗"同样在服务范围内。

最后成文作答并标注引用；范围外的问题直接拒答并说明服务边界。

## 架构

### 请求链路

```
HTTP 请求
  │
  ▼
RagController  /api/rag/chatAgent/multi
  │  resolveUserId：token → UserContext，缺失回落 1L
  ▼
MultiAgentRagServiceImpl        编排层：读历史 → 跑图 → 回写记忆
  │
  ▼
外层状态图（LangGraph4j）
  │
  ├─ ScopeCheck   范围闸：硬拒域外 / 强放域内 / LLM 兜底
  │               + 意图识别（retrieve / both / calculate / review）
  │                 ├─ 域外 ─────────────→ END（拒答，省掉后续检索与生成）
  │                 ├─ review ─────────→ ClauseReviewer（合同审查分支）
  │                 └─ 其他 ↓
  ├─ Retriever    调内层检索子图 → 得到条款依据
  │               按意图门控触发计算（违约金 / 借贷利息）
  │                 │
  │                 ▼
  │        ┌──────── 内层检索子图（AgenticRagGraph）────────┐
  │        │  retrieve  BM25 ∥ KNN 召回 → 加权 RRF 融合      │
  │        │     ↓                                          │
  │        │  grade      LLM 逐条打分「相关|分数」，阈值 0.6  │
  │        │     ├─ 过门 ─────────────────────→ generate     │
  │        │     └─ 全灭 → rewrite 改写查询 → retrieve      │
  │        │              （最多改写 2 次，仍全灭则拒答）    │
  │        └────────────────────────────────────────────────┘
  │                 ↓
  ├─ Answer      确定性模板拼接：条款锚定 + 检索成文 + 引用 + 计算结论
  │              （不额外调 LLM，结果可复现）
  │                 ↓
  ├─ ClauseReviewer   合同审查分支入口（review 意图时取代 Answer）
  │              条款切分 → 逐条审查 → 聚合审查报告
  │                 ↓
  └─ Critic      评审充分性：启发式 + LLM
                ├─ 不足且未达上限 → 回到 Retriever（重规划重检索）
                └─ 充足 → END
  │
  ▼
返回答案（问答含引用条款号；审查为风险清单与改写建议）
```

### 为什么是两层图

外层管**该不该答、答得对不对**（范围、计算、评审），内层管**答得有没有依据**（检索、评分、改写）。
分开的好处是检索可以独立复用与单测——外层 `Retriever` 调内层时只关心"拿到条款没有"，
不关心检索是几路召回、评分阈值多少。

### 记忆层

| 存储 | 键 | 内容 | TTL |
|---|---|---|---|
| 会话历史 | `memory:history:{sid}` | 最近 10 轮原文，超窗压成滚动摘要 | 7 天 |
| 约束事实 | `memory:calcparams:{sid}` 等 | 本金 / 天数 / 利率 / calcType / 条款锚点 | 7 天 |
| 用户画像 | `user:profile:{uid}` | 咨询领域（合同/劳动/婚姻/借贷等）/ 偏好 / 常问 / 纠错 | 30 天 |

约束事实走**独立键**而非塞进历史文本——历史会被摘要压缩，数值不能跟着一起丢。

### 合同审查链路

`review` 意图由 ScopeCheck 分流到 ClauseReviewer，取代常规问答路径。核心是**审查点驱动**：
每条款先判定审查维度，再按维度分派到对应审查逻辑，而不是"先看有没有异常信号再决定要不要问模型"。

```
合同文本 → 切分条款（引言与无编号整段不参与审查）
  │
  ├─ 逐条审查
  │    ├─ 分类 + 风险判定 ← 一次 LLM 调用，按条款文本 hash 缓存
  │    │    产出：审查维度 / 是否有风险 / 风险描述 / 法律依据 / 改写建议
  │    ├─ 数值类 → 确定性规则校验（不依赖 LLM）
  │    │    · 借贷利率 > 4×LPR 日千分比 0.378‰
  │    │    · 违约金比例 > 30%（民法典 585 条参照线）
  │    ├─ 语义类 / 格式类 → 以 LLM 判定为准
  │    │    · 无检索依据（RRF < 0.03）时直接提示风险
  │    └─ 无关类 → 跳过语义判断
  │
  └─ 合同级完备性检查（与逐条审查并行）
       8 项要素：主体 / 标的 / 数量 / 交付时间 / 价款 / 违约责任 / 争议解决 / 生效条件
       触发门槛：条款数 ≥ 2（或无编号但有实质内容）且缺失 ≥ 2 项
```

**LLM 与规则的分工是这个设计的重点**：

| 判定类型 | 交给谁 | 原因 |
|---|---|---|
| 数值大小（利率、违约金比例） | **规则** | 小模型对「千分之一 vs 百分之三十」这类比例换算不可靠，实测会把合法偏低的违约金判为过高 |
| 权利义务是否失衡、免责、解释权 | **LLM** | 需要语义理解，规则无法穷举 |
| 合同缺哪些要素 | **规则** | 固定检查项，零 LLM 成本、可解释可回归；LLM 判定倾向说"未明确"，会误报法定管辖等合法写法 |
| 分类 + 风险定性 | **LLM 一次** | 合并为单次调用省一次网络往返，结果按文本 hash 缓存 |

```bash

   src/main/resources/application-local.yml
```

## API

统一前缀 `/api/rag`。除 `/api/memory/**` 需强制 JWT 外，其余接口在携带合法 token 时走
`UserContext` 解析真实用户，缺失时回落 `userId=1`（便于本地调试与评测）。

### 多智能体问答

| 方法 | 路径 | 参数 | 说明 |
|---|---|---|---|
| GET | `/chatAgent/multi` | `kbId` `sessionId` `question` | 生产端点，返回答案 |
| GET | `/chatAgent/multiDebug` | 同上 | 额外返回 `meta`，供量化评测消费 |

`multiDebug` 的 `meta` 含 5 个字段：

| 字段 | 含义 |
|---|---|
| `retrieved` | 命中的条款片段（含 `clauseId` 与融合分数） |
| `extracted` | 从问题中抽出的计算参数（本金 / 天数 / 日利率‰） |
| `computed_penalty` | 计算结果金额 |
| `rejected` | 是否因范围或检索失败而拒答 |
| `replanned` | Critic 是否触发了重规划重检索 |

### 单图检索与单轮问答

| 方法 | 路径 | 参数 | 说明 |
|---|---|---|---|
| GET | `/chatAgent/stream` | `kbId` `sessionId` `question` | 单图 AgenticRAG，不做范围判定与评审 |
| GET | `/chat/stream` | `kbId` `sessionId` `question` | 单轮 RAG，SSE 流式 |
| GET | `/chat/history` | `sessionId` | 会话历史 |

### 知识库管理

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/kb/create` | 新建知识库 |
| GET | `/kb/list` | 列出可见知识库（自己的 + 公共） |
| POST | `/document/upload` | 上传文档（解析 → 切片 → 向量化 → 入库） |

## 核心设计决策

### 1. 范围判定用规则快路径 + LLM 兜底，而不是全交给模型

`ScopeCheck` 先走规则：命中硬拒词表直接拒答，命中锚点词（如"合同"）直接放行，
只有规则不确定时才调 LLM 分类。原因是范围判定的错误代价不对称——把域内问题误拒
比误放代价大得多，而全交给 LLM 又会为每个请求多付一次模型调用的延迟。
规则表能覆盖绝大多数问法，兜底只处理长尾。

### 2. 检索用加权 RRF，KNN 权重高于 BM25

两路召回各自有盲区：BM25 擅长条款编号与专有名词（"第585条"这种字面命中），
KNN 擅长同义表述（"逾期违约金" vs "迟延履行违约金"）。融合用 RRF 而非归一化分数相加——
两路分数量纲不同，相加需要额外校准，RRF 只用排名，对量纲免疫。

关键在权重：KNN 1.0 / BM25 0.3。BM25 权重压低是因为它会带回大量"字面沾边但语义无关"的
噪声片段，这些噪声在等权融合里会稀释真正的语义命中。平滑常数 k 取 10 而非默认 60，
因为 k=60 会把各列表内部的排名差异压平，接近 KNN-only 的上限。

`rag.hybrid.knn.enabled` 留了开关，关掉即退化为纯 BM25，便于对比评测两种配置。

### 3. 评分门用轻量模型，阈值 0.6，改写重试有上限

检索召回后不直接生成，而是让 LLM 逐条判「相关|分数」，只留 ≥ 0.6 的片段。
这一步是防"检索到了但答非所问"——召回片段里常混着仅关键词重合的条款。
打分用 Qwen-Flash 而非主模型，因为这是短输出高频调用，成本敏感。

全灭时改写查询重检，但**上限 2 次**。不设上限会陷入"改写→召回→评分全灭→再改写"的空转，
既烧 token 又拖延迟；改写本身也可能抛错，所以重试计数在改写失败时也要累加。

### 4. Answer 用确定性模板拼接，不调 LLM

检索节点已经把依据写成文（内层 generate 产出），如果 Answer 再调一次 LLM 做综合，
等于同一件事做两遍。所以 Answer 走模板拼接：上轮条款锚定 + 检索成文 + 引用依据 + 计算结论，
四段拼起来。好处是结果可复现、可审计，且省一次模型调用——法律问答里"同样输入得到同样答案"
本身是需求。

### 5. 约束事实用独立 Redis 键，与自由文本历史隔离

短期记忆里，文本历史会被滑窗截断、超窗后还会被摘要压缩。但本金、天数、利率、已锚定的
clauseId 这些是**硬约束**，走摘要会丢精度——第二轮用户只说"改成 45 天"，如果本金在摘要里
被压掉了就算不出数。所以这些字段存在独立键里，跨轮继承走 `getCalcParams` 而非读历史。

长期用户画像（咨询领域/偏好）是**软提示**，召回后软注入 prompt，绝不覆盖短期状态——
软提示猜错了不该让数值计算跟着错。

### 6. 工具调用手写 ReAct 循环，不依赖 SDK 的 function calling

DashScope Java SDK 的 function calling 支持不稳定，所以工具循环是自己实现的：
解析模型输出的 JSON → 调 `ToolExecutor` → 把结果回填 → 再让模型判断下一步。
代价是要自己处理解析容错，收益是与 SDK 版本解耦、可控、可调试——工具入参非法时
返回提示让模型重试，而不是抛异常打断链路。

### 7. 审查数值类不交给 LLM 判定

实测 qwen-flash 把「违约金按未履行部分价款的**千分之一**支付」判为「比例过高，
可能被法院调整」——千分之一是 0.1%，属于合法偏低。这类错误的危险在于
**解释听起来完全合理**，不容易被发现。

所以数值是否越界只由确定性规则判定（利率超 4×LPR、违约金超 30%），
LLM 只负责它擅长的语义判断（权利义务是否失衡、免责、解释权）。
代价是数值类条款的建议描述更笼统，接受——**宁可描述笼统，不可结论错误**。

### 8. 没做关键词白名单，改用合并调用 + 缓存

曾做过 9 个词的白名单（"诚信原则""应当遵循"等）跳过审查，A/B 实测只省 0.9s/题。
但构造用例发现 5 条免责条款全部因含这些词被整条跳过——裸 `contains` 匹配
分不清中性表述和免责条款。**白名单省的是钱，漏的是风险，这两者不能trade。**

改为「分类 + 风险判定合并为一次 LLM 调用」加「条款文本 hash 缓存」，
耗时反而降到 0.9s，比白名单版更快且不漏检。

### 9. 完备性检查用规则不用 LLM

LLM 判定倾向于说"未明确"——8 条误报的根因统一为「要求条款写到更细」，
连"有管辖权的人民法院"这种法定管辖写法都被判成管辖不明。而合同法允许
对未约定事项作法定补充。规则版本可解释、可回归、零 LLM 成本。

## 评测指标

数据来自仓库外的评测脚本，测试集与结果文件不入库（见 `.gitignore`）。

### 检索（150 题，graded 门后口径）

| 指标 | 数值 |
|---|---|
| HR@1 / HR@3 / HR@5 | **0.741 / 0.885 / 0.950** |
| MRR | **0.825** |
| amount_acc | 1.0（字段级 principal / days / rate 全1.0） |
| 拒答 recall / precision | 1.0 / 0.846（TP11 FN0 FP2 TN137） |

拒答 precision 未达1.0 的原因已定位：拒答判定依赖答案文本匹配，重规划轮中
LLM 复述「无法作答」字样时被误标为拒答，2 道域内题受影响；两题的检索结果正常。
属既有判定方式的脆弱点，非检索能力问题。

### 合同审查（18 题，规则判定）

| 指标 | 数值 |
|---|---|
| 路由正确率 | 100%（18/18） |
| 高风险检出率 | 100%（9/9） |
| 缺失条款检出率 | 100%（6/6） |
| 正常条款误报率 | 0%（0/3） |

### 这些数字的适用边界

**检索指标不是真实场景水位。** 150 题是clause→question 反推生成的——先取 gold 条款、
再让 LLM「为每条条款生成提问」，问题几乎是条款的语义复述，Q↔条款对齐过紧，
rank1 命中率 74.1%。用 30 道非反推独立命题（真实口语问法 + 盲标 gold）复测，
真实 HR@5 约 **0.43**（30 样本，区间 0.27–0.59）。真实短板在口语与多事实问法的检索。

**审查的 100% 是规则可判题型下的成绩。** 18 题是按「能否用规则判定检出」设计的：
高风险题只覆盖数值超限、权利义务失衡、表述模糊三类；缺失题只覆盖 8 项固定要素。
改写建议的质量没有金标、不纳入评分。真实合同里更常见的风险类型（如知识产权归属缺失、
通知送达条款缺失）目前不在检查项内。

换句话说：**这两个数字证明的是链路正确、判定可复现，不是模型能力强。**
