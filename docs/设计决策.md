## D1. 范围判定：规则快路径 + LLM 兜底

**处境**
一个 12 法域的法律问答系统，必然会收到范围外的问题（商标、税务、股东、消费者权益）。
范围判定的错误代价不对称：把域内问题误判为域外，用户空手而归，体感极差；
而把域外问题误判为域内，顶多给出一次不相关的拒答或牵强作答。

**选择**
不把范围判定完全交给 LLM，而是三级：
1. **硬拒**——命中域外关键词表（如"商标注册""报税"）直接拒
2. **强放**——命中域内锚点词（如"合同"）直接放行
3. **LLM 兜底**——前两级都不确定时才调模型分类

**代价 / 取舍**
规则表需要人工维护，遇到新问法可能漏。实测中"怎么离婚""工伤怎么赔""试用期违法吗"
这些都不在硬拒表里（因为它们其实在服务范围内），需要走 LLM 兜底——
这会多付一次模型调用。这是有意接受的：宁可多付一次调用，也不要为了省调用而误拒。

**如果重做**
会考虑把规则表做成可配置项（放数据库或配置中心），让服务范围变化时不用改代码。
当前是硬编码在代码里的，改范围要重新发版。

## D2. 检索融合：加权 RRF，KNN 权重高于 BM25

**处境**
法规检索里两类查询都常见：查条款编号（"第585条"）和查语义（"逾期违约金怎么算"）。
单一召回方式都有明显盲区——纯 BM25 召不回换了措辞的同义表述，纯向量对条款编号不敏感。

**选择**
双路召回 + 加权 RRF 融合。权重 **KNN 1.0 / BM25 0.3**，平滑常数 **k = 10**。

**推导过程**
RRF 公式 `score(d) = Σ w_r / (k + rank_r(d))` 只吃排名，两路分数量纲不可比的问题自然消失
（BM25 分数无上界，KNN 余弦落在 [-1,1]，归一化相加需要额外分母，且分母随库规模漂移）。

权重和 k 是调出来的，不是拍的：
- **BM25 压到 0.3**：BM25 会在条款编号、专有名词上产生大量字面命中，这些片段语义上常无关。
  等权时它们挤占前列，把语义命中的真条款挤下去。
- **k 从 60 降到 10**：k 控制排名差异被压平的程度。k=60 时 rank1 与 rank10 的得分比
  仅约 1.15，几乎抹平——但向量召回内部的排名恰恰是最有价值的信号。取 10 时该比值约 1.45。

**代价 / 取舍**
权重与 k 是**经验值**，绑定当前知识库规模（2186 条 / 12 法域）。
若扩到万级异质库，权重的最优值会漂移，需要重标定。这是已知的技术债，
`application.yml` 里把参数做成可配置就是为了将来能不改代码重调。

**可复现性**
`rag.hybrid.knn.enabled` 保留开关，关掉即退化为纯 BM25，
便于对比两种配置下的表现，而不是靠记忆去猜"当时是什么配置跑出来的数"。

## D3. 评分门：轻量模型 + 阈值 0.6 + 改写重试上限 2 次

**处境**
向量召回的 top-50 里混着大量"关键词重合但语义无关"的片段。
直接把这些丢给生成模型，它会拿着噪声编答案——这在法律场景是不可接受的。

**选择**
三段式：
- 召回后不直接生成，先让 LLM 逐条判「相关|分数」，只留 ≥ **0.6**
- 全灭时改写查询重检，**上限 2 次**
- 打分用 Qwen-Flash 而非主模型

**推导过程**
0.6 是经验值：低于 0.5 会把"措辞相近但实质不同"的条款放进上下文（干扰生成）；
高于 0.7 则容易把可用的表述判掉。0.6 是多次目视检查过门/被门片段后的折中。

改写用轻量模型是成本考虑——这一步是高频短输出调用，若用主模型，
单次成本会翻几倍，而它的任务只是"换个说法重查"，不需要强推理。

**代价 / 取舍**
`retryCount` 上限是**必须**的：不设上限会陷入"改写→召回→评分全灭→再改写"的空转，
既烧 token 又拖延迟。更隐蔽的是——**改写本身可能抛错**，若抛错时不累加重试计数，
图会在 rewrite 与 retrieve 之间无限循环。所以现在改写失败也会 `retryCount + 1`。

**遗留问题**
评分依赖 LLM 输出的格式，正则解析失败时按"不相关"处理，等于静默丢弃该片段。
更好的做法是解析失败时重试一次，或降级为纯 BM25 门控。当前没做。

## D4. Answer 走确定性模板，不再调 LLM

**处境**
内层检索子图的 generate 节点已经把依据成文了（带引用标注）。
如果 Answer 节点再调一次 LLM 做"综合"，等于同一件事做两遍，多花一次调用且引入不确定性。

**选择**
Answer 用确定性模板拼四段：
```
上轮条款锚定（多轮追问保上下文）
+ 检索成文（内层 generate 的产出）
+ 引用依据（clauseId + content）
+ 计算结论（computedPenalty + extractedParams）
```

**为什么值得**
1. **省一次 LLM 调用**——链路从 3 次模型调用降到 2 次
2. **结果可复现**——同样输入必得同样输出，法律场景里这是硬需求，
   而不是"体验更好"这种软理由
3. **可审计**——答案的每一段都能追溯到具体来源，监管场景下这是刚需

**代价 / 取舍**
模板拼接的文��不如 LLM 灵活。如果需要根据问题类型调整表述结构，
模板会变得难维护。当前问题域固定（法律条款问答），这个代价可以接受。

## D5. 约束事实用独立 Redis 键，与文本历史隔离

**处境**
短期记忆用滑窗保留最近 10 轮，超窗后最早的部分会被摘要压缩。
用户第二轮只说"改成 45 天"——本金、天数、利率必须还在。

**选择**
把这些"硬约束"从文本历史里拿出来，存独立键：

```
memory:calcparams:{sid}   本金 / 天数 / 利率
memory:calctype:{sid}     上轮算法类型
memory:docscur:{sid}      上轮命中的 clauseId
```

跨轮继承走 `getCalcParams` 这样的确定性读取，不读历史文本。

**推导过程**
历史文本会被**有损压缩**——摘要的目标是省 token，不是保精度。
把 1000000.0 压成"约100万"看似无害，但利率、期限这些值一旦被概括，
计算结果就错了。硬约束不能承担这种风险。

**对称的另一面**
长期用户画像（合同类型、偏好）是**软提示**，召回后软注入 prompt，绝不覆盖短期状态。
理由：画像是模型对用户偏好的**猜测**，可能错。软提示猜错了影响表述风格是可接受的，
硬覆盖会让数值计算跟着错——错误的方向完全相反。

**代价 / 取舍**
两套键空间意味着一致性维护成本：新增约束字段时要同时更新 entity、序列化与清理逻辑。
换来的是"数值不会被摘要弄丢"这个硬保证。

## D6. 手写 ReAct 工具循环，不依赖 SDK 的 function calling

**处境**
需要让模型决定是否调用工具（算违约金、查条款）并把结果回传再让它继续判断。
DashScope Java SDK 提供了 function calling，但对本项目的模型与版本组合支持不稳定。

**选择**
自己实现 ReAct 循环：解析模型输出的 JSON 工具调用 → `ToolExecutor` 分发 →
结果回填 → 再让模型判断下一步。

**代价 / 取舍**
要自己处理解析容错、格式漂移、多轮拼接。收益是与 SDK 版本解耦：
模型或 SDK 升级不会让工具调用链路静默失效——这是可控性换开发速度。

**工具入参非法时**返回提示让模型重试，而不是抛异常打断链路。
因为一次参数错误不该让整个问答失败，模型通常能自己纠正。

**具体实现**
工具只暴露两个：`calculate_penalty`（算金额）、`cite_clause`（按查询召回条款作引用）。
刻意保持工具数量少——工具一多，模型选错工具的概率上升，每个工具的描述都要更精确。

## D7. Git 历史清理：不重建仓库，用 filter-repo 重写

**处境**
项目早期提交把含明文密钥的配置文件和脚本推到了公开仓库：
DashScope key、Coze token、旧 JWT 签名密钥、微信 secret、百度 OCR key、公网 IP。

**选择**
1. 先完整备份（`.git` 目录 + 全部未提交改动的 patch + 未跟踪文件打包）
2. `git filter-repo --invert-paths` 移除配置文件路径
3. `git filter-repo --replace-text` 替换 Java 源码里的硬编码密钥
4. `git push --force --mirror` 强推
5. 全历史扫描验证

**为什么不重建仓库**
重建（`rm -rf .git && git init`）更简单，但会丢掉全部提交历史——
对一个已有 5 个提交、记录了功能演进过程的项目是破坏性的。
filter-repo 能保留 commit 结构与提交信息，只重写内容。

**为什么不用 `git filter-branch`**
官方已标记为过时，且在 Windows 中文路径环境下问题多。filter-repo 是官方推荐替代。

**强推的代价**
所有协作者需要重新 clone 或 `git reset --hard`。单人项目可接受。

**关键教训**
> 清理历史 ≠ 清理工作区。
> 第一次 `git add -A` 提交时，把**工作区里**的旧密钥又写回了历史——等于白做。
> 正确顺序是：**先脱敏工作区 → 再 commit → 再验证**。

**另一个教训**
做破坏性 git 操作前，**必须先 `git add -A && git commit` 固化全部改动**，
不能只靠 `git diff` 做备份。"已暂存但内容还在工作区"的文件，
`git diff --cached` 只会抓到空 blob，`ls-files --others` 又抓不到（已暂存≠未跟踪），
两种备份方式恰好都漏掉这一类。

## D8. 审查数值类不交给 LLM 判定

**决策**：审查点分类为「数值」的条款，是否违规只由确定性规则判定，
LLM 的判定结果在这条路径上不参与风险结论。

**背景**：合同审查里有两类判定混在一起——数值是否越界（利率、违约金比例），
以及权利义务是否失衡（解释权归一方、单方解除、免除全部责任）。前者本质是
阈值比较，后者需要语义理解。第一版把两类都交给 LLM，实测暴露一个问题：
qwen-flash 把「违约金按未履行部分价款的**千分之一**支付」判为
「违约金比例过高，可能被法院或仲裁机构调整」。

**为什么**：千分之一是 0.1%，属于合法偏低的约定；模型误判的原因是
「千分之一」与「百分之三十」之间的量级换算不可靠。这类错误有两个特点：
一是方向不确定（可能高估也可能低估），二是**看起来合理**——它的解释听起来
完全像那么回事，不容易被发现。

**代价**：数值类条款的风险描述与改写建议质量下降（规则只能给出
「超出法定上限」这类结论，说不出具体怎么改）。接受这个代价——
宁可描述笼统，不可结论错误。

**通用原则**：**数值结论交给规则，语义结论才交给 LLM。**

## D9. 下线关键词白名单，改用合并调用 + 结果缓存

**决策**：审查点分类前不做关键词白名单短路，每条款都过一次 LLM 分类；
成本用「分类与风险判定合并为单次调用」加「按条款文本 hash 缓存结果」来补。

**背景**：为了省 token，先做了 9 个词的规则白名单（「诚信原则」「应当遵循」
「按照约定履行」等），命中即判为"无关"、跳过审查。用同一构建做了 A/B 实测。

**为什么否决**：

1. **漏检真实风险**。构造 5 条含白名单词的免责条款，全部被整条跳过——
   例如「甲方因不可抗力造成的损失**应当遵循**当地惯例由甲方自行承担全部责任」
   因含「应当遵循」被判为无关。裸 `contains` 匹配没有任何否定词或风险信号检查，
   而免责、弃权、单方权利这类条款天然会包含中性表述词。
2. **收益不匹配**。A/B 实测白名单只省 0.9s/题（2.4s → 3.3s），
   换来的是漏检。合同审查场景下漏检的代价比多花 0.9s 大得多。
3. **更严重的是，A/B 测不出它**。18 题测试集里白名单只命中 2 题且都是正常条款，
   样本量不足导致两个分组指标几乎无差异——**如果只看 A/B 数据就上线，
   这个缺陷会一直藏着**。是构造用例才暴露出来的。

**替代方案的实测效果**：合并调用省掉一次网络往返（分类 0.78s 消失），
缓存让重复审查接近零成本，两项合计使平均耗时从 2.4s 降到 0.9s——
**比白名单版本更快，同时不漏检**。

**附带认识**：白名单省的是钱，漏的是风险。这两者不对称，不能 trade。

## D10. 合同级完备性检查用规则，不用 LLM

**决策**：缺哪些要素用 8 项固定检查 + 正则判定，不引入 LLM 参与。

**背景**：「这份合同是否缺少争议解决条款」这类问题，
看起来该让 LLM 判断，因为它需要理解整份合同。评估后选了规则。

**理由**：

1. **「缺什么」是整份合同的属性，逐条款分类天然测不出来**。分类是对单条款
   打标签，而完备性需要对条款集合做统计——两者不是同一层问题。
2. **LLM 判定会重新引入误报**。审查 18 题中有 8 条误报，根因统一为
   「要求条款写到更细」：把「有管辖权的人民法院」判成管辖不明确、
   把「收到货物后 7 日内」判成起算点不清。而合同法允许对未约定事项作法定补充，
   买卖合同的交付时间地点可按交易习惯确定。这些都是合法常见写法。
3. **规则可解释可回归，零 LLM 成本**。缺哪些要素一目了然，
   改阈值就能调整严格程度，不需要重跑模型。

**双阈值防误报**：条款数 ≥ 2 才检查（单条款片段不算合同），
且缺失 ≥ 2 项才提示（缺 1 项通常是正常书写差异）。
两个阈值都是踩过坑之后加的——最初没有阈值时，
「双方应遵循诚信原则履行合同义务」这种单条款被报出 7 项缺失。

**与 D8、D9 的一致性**：三者指向同一个原则——
**能用确定性方法判定的，不要交给概率模型**。D8 守数值，D10 守结构，
D9 守的是"不要用会漏检的捷径"。

## 附：还没做的取舍

| 想做 | 为什么没做 |
|---|---|
| 切片按语义边界切 | 当前定长切分（1500/200 重叠）实现简单、够用。语义边界切分要先做条款结构识别，成本更高，暂缓 |
| 查询向量缓存 | 每次检索都重算 embedding。QPS 低时无所谓，高 QPS 下是瓶颈 |
| `chatStream` 接真 SSE | DashScope 侧未接 stream 接口，需确认 SDK 能力后评估 |
| ES 版本升到 8.15.5 | 8.15.0 缺 `KnnQuery.Builder.k()`，用 `size()` + 固定 `numCandidates` 绕过了。升级需重跑评测确认水位不退 |
| 完备性检查交给 LLM | D10 已说明：会引入误报，且规则版本可解释可回归 |
| 审查要素从 8 项扩到更多 | 知识产权归属、通知送达、不可抗力定义等确实常见，但每加一项都要重跑评测确认误报率不升。当前 8 项覆盖的是缺任一项即影响合同成立的要素 |
| 长合同（30+ 条款）批量优化 | 逐条串行调用，5 条合同约 2.2s。30 条会到 13s 左右。并行化需要先处理 LLM 调用的限流与结果合并 |
| 改写建议质量评估 | 改写是 LLM 自由生成，没有可复现的金标。想过用「引用原文对比」做弱校验，但很难量化"改得好" |
