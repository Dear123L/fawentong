# 架构说明

本文补充 README 中未展开的架构细节：状态图机制、检索链路、记忆层、失败处理策略。

## 一、为什么用状态图而不是顺序调用

法律问答不是"问一句答一句"的直线流程，它有三个天然的分叉：

1. **该不该答**——域外问题要拒答并说明边界，这需要在检索之前就知道，否则白花钱
2. **要不要算**——只有涉及金额的问题才触发计算，纯概念问答不该跑计算
3. **答得够不够**——检索到的条款可能不足以支撑答案，需要回头重检索

用 if-else 串起来会让这三处分叉互相嵌套。用状态图（LangGraph4j）之后，每个分叉
是一个节点 + 条件边，拓扑一眼可见，状态（state）贯穿全图。

## 二、状态与"为什么必须返回增量 Map"

LangGraph4j 的 `AgentState.data()` 是 `final` 且返回**不可变视图**——节点内部
`state.data().put(...)` 会抛 `UnsupportedOperationException`。因此约定：

> **节点返回「本次要更新的字段 Map」，由框架合入状态。**

这条约定让状态写入点唯一可控：想看某字段被谁改过，只需 grep 各节点返回的 Map。
如果允许节点直接改状态，多节点并发写时就无法判断字段归属。

## 三、两层图的职责切分

| | 外层（MultiAgentGraph） | 内层（AgenticRagGraph） |
|---|---|---|
| 节点数 | 5：ScopeCheck / Retriever / Answer / ClauseReviewer / Critic | 4：Retrieve / Grade / Rewrite / Generate |
| 职责 | 该不该答、答得对不对 | 答得有没有依据 |
| 是否感知 userId / 会话 | 是（长期记忆召回、跨轮锚定） | 否（纯检索能力） |
| 是否可独立复用 | 否 | 是（`/chatAgent/stream` 直接调） |

内层图不感知用户与会话，因此可以被单图端点直接复用，也可以被外层 Retriever 复用——
同一套检索能力，两种入口。

## 四、合同审查分支拓扑

`review` 意图从 ScopeCheck 直接分流到 ClauseReviewer，绕过 Retriever 与 Answer。
该分支与问答路径共享 ScopeCheck 与 Critic 两个节点，中间环节完全不同。

```
START
  │
  ▼
ScopeCheck  ─── 意图 = review ──→ ClauseReviewer ──→ Critic ──→ END
  │                                                ▲
  │ 意图 = retrieve / both / calculate             │
  ▼                                                │
Retriever ──→ Answer ──────────────────────────────┘
```

ClauseReviewer 自身不做判定，只调用 `ClauseReviewEngine` 并把报告写入状态：

```
合同文本
  │
  ▼
切分条款  ── 引言块（首条款前的提问文本）与无编号整段不参与审查
  │
  ▼
逐条审查（主循环）
  │┌─────────────────────────────────────────────┐
  ││ ①分类 + 风险判定 ← 一次 LLM 调用             │
  ││    输入：条款原文 + 检索到的法规依据 + 数值校验│
  ││    产出：维度 / 是否有风险 / 风险描述 /        │
  ││          法律依据 / 改写建议                  │
  ││    缓存：条款文本 SHA-256 → Redis，TTL 7 天   │
  ││                                             │
  ││ ② 按维度分发                                 │
  ││    数值类 → 确定性规则（利率、违约金比例）    │
  ││    语义类 → LLM 判定为准                     │
  ││    格式类 → LLM 判定为准                     │
  ││    无关类 → 跳过语义判断                     │
  ││    兜底   → 无检索依据（RRF<0.03）直接提示   │
  │└─────────────────────────────────────────────┘
  │
  ▼
合同级完备性检查（与逐条审查并行）
  8 项要素：主体 / 标的 / 数量 / 交付时间 / 价款 /
           违约责任 / 争议解决 / 生效条件
  触发：条款数 ≥ 2（或无编号但有实质内容）且缺失 ≥ 2 项
  │
  ▼
聚合为纯文本审查报告
```

**为什么审查要独立成分支而不是塞进 Answer**：审查的产出是风险清单而非问答，
需要逐条切分、逐条判定依据强度，还要在整份合同维度做完备性检查——
与"给定问题→检索→成文"的问答流程没有可复用的中间状态。

### 数据流对比

| | 问答路径 | 审查路径 |
|---|---|---|
| 意图 | retrieve / both / calculate | review |
| 入口节点 | Retriever | ClauseReviewer |
| 检索用途 | 为问题找依据（topK 召回 + 评分门） | 为条款找依据（逐条 top5 召回） |
| 判定主体 | 规则 + LLM 混合，按意图门控 | 审查点驱动：先分维度再分派 |
| LLM 调用 | 生成答案 + Critic 评审 | 分类与风险定性（合并为一次） |
| 输出 | 答复 + 引用条款号 | 风险清单 + 改写建议 + 依据 |
| Critic 行为 | 不足则回到 Retriever 重规划 | 强制视为充足，直接结束 |

## 五、检索链路细节

### 5.1 混合召回

```
                 ┌─ BM25: match(content) 过滤 kbId ─→ rank_bm25
query ───────────┤
                 └─ KNN:  knn(vector) 过滤 kbId ────→ rank_knn
                          │
                          ▼
              加权 RRF 融合
    score(d) = Σ_r  w_r / (k + rank_r(d))
      w_knn = 1.0   w_bm25 = 0.3   k = 10
                          │
                          ▼
                同一 clauseId 在两路出现则分数累加
```

**为什么 RRF 而不是分数归一化相加**：BM25 分数无上界且分布随查询长度变化，KNN 余弦
相似度落在 [-1,1]，两者量纲不可比。归一化需要引入额外参数（min-max / z-score 的分母），
而这些参数随知识库规模漂移。RRF 只吃排名，天然免疫量纲问题。

**为什么 k 取 10**：RRF 的 k 控制"排名差异被压平的程度"。k=60（标准默认值）会让
rank=1 与 rank=10 的得分比只有 (1/61)/(1/70) ≈ 1.15，几乎抹平——但向量召回内部
的排名恰恰是最有价值的信号。取 10 时该比值约 1.45，保留住了内部区分度。

**为什么 BM25 权重压到 0.3**：BM25 会在"条款编号""专有名词"上产生大量字面命中，
这些片段语义上可能完全无关。等权融合时它们挤占前列，把语义命中的真实条款挤下去。

### 5.2 评分门

```
召回片段 ─→ LLM 逐条打分「相关|0.87」 ─→ 保留 ≥ 0.6 ─→ 送 generate
                        │
                   全灭则改写查询重检（上限 2 次）
```

这一步解决"召回到了但答非所问"。向量召回的 top-50 里常混着仅关键词重合的条款，
直接生成会让 LLM 拿着噪声编答案。评分门把这类片段挡在外面。

打分用 Qwen-Flash：高频、短输出、成本敏感。阈值 0.6 是经验值——低于 0.5 会把
措辞相近但实质不同的条款放进上下文，高于 0.7 则容易把可用的表述判掉。

### 5.3 拒答的两条路径

1. **范围拒答**：ScopeCheck 判定域外，直接短路到 END，不检索不生成
2. **检索拒答**：评分门全灭且改写次数用尽，Generate 直接返回固定话术

两条路径的拒答文案都会被外层 Retriever 用 `contains` 匹配转成 `rejected` 标记，
供评测统计拒答精确率与召回率。**改文案时必须同步改这个匹配逻辑。**

## 六、计算链路

```
intent ∈ {both, calculate}  才触发计算（ScopeCheck 的门控）
  │
  ▼
CalcRegistry.route(question)
  含「利息/利率/借贷/借款/贷款/借了」→ LOAN_INTEREST
  其余                                     → PENALTY（兜底）
  │
  │ 跨轮：本轮无触发词但命中改写词（改成/如果/变成/天/利率/本金/金额/呢）
  │      且上轮算过 → 继承上轮 calcType
  ▼
PenaltyCalculatorAdapter / LoanInterestCalculator
  日万分之五 = 0.5‰；年化上限 4×LPR = 13.8%
```

**为什么计算要门控**：不是每个法律问题都要算钱。门控让纯概念问答（"违约金怎么定"）
跳过整条计算链路，省一次 LLM 意图判断之外的调度开销。

**为什么有跨轮继承**：用户第二轮只说"改成 45 天"，本轮没有借贷类关键词。
若不回退到上轮的算法类型，45 天会被当成违约金而不是利息，结果错误。
触发词表是"回填型"措辞（改成/变成/如果/天/利率/本金）。

## 七、记忆层设计

### 7.1 短期：滑窗 + 结构化键隔离

```
memory:history:{sid}       最近 10 轮原文，超窗后最早的部分压进 memory:summary:{sid}
memory:calcparams:{sid}    本金 / 天数 / 利率          ← 硬约束
memory:calctype:{sid}      上轮算法类型                ← 硬约束
memory:docscur:{sid}       本轮命中的 clauseId         ← 硬约束
```

**核心决策：硬约束不放进文本历史。**

历史会被截断与摘要压缩，而数值精度不可压缩。用户在第二轮说"改成 45 天"，
若本金只存在于历史摘要里，摘要一压缩就可能丢精度，算出来的数就是错的。
独立键让跨轮继承走 `getCalcParams` 这样的确定性读取，不依赖摘要质量。

### 7.2 长期：摊销抽取 + 软注入

```
user:profile:{uid}        Hash: contracts / preferences / freqQA / corrections / lastActive
user:extractcnt:{sid}     计数器，每 3 轮才调一次 LLM 抽取
```

**为什么要摊销（每 3 轮）而非每轮抽取**：每轮都调 LLM 抽取画像，成本和延迟都不可接受。
摊销后摊到单轮的边际成本接近零。

**为什么是软注入**：画像是模型对用户偏好的猜测，可能错。若硬覆盖短期状态，
一次错误猜测就会让数值计算出错。软注入（追加到 prompt 供模型参考）让画像
影响"表述风格"而非"计算依据"。

### 7.3 召回方式

当前用中文 bigram 重叠度算相关度召回，不依赖向量。原因是画像片段量级很小
（一个用户几十条），bigram 足够，且省掉一次 embedding 调用。

## 八、失败处理策略

统一原则：**失败不传染**——任何节点异常都不应让整条链路崩掉。

| 节点 | 异常时 | 理由 |
|---|---|---|
| ScopeCheck | 放行（走正常检索） | 宁可多答一次，也不要误拒 |
| Retrieve | 写"检索失败" handoff，retrievedDocs 置空 | 后续节点有占位可处理 |
| Grade | 全部放行（不做门控） | 评分是优化项，不该因单点故障丢依据 |
| Rewrite | 沿用原查询，但**仍累加重试计数** | 改写抛错若不计数会空转 |
| Generate | 返回固定失败话术 | 不编造 |
| Critic | needsMore=false | 绝不无限重试 |
| 记忆落库 | 只记日志，不阻断主问答 | 记忆失败不该让用户看不到答案 |

## 九、已知短板

诚实记录，避免误判系统能力：

1. **切片是定长切分**，未按条款/段落语义边界切。一条完整条款正好被切断时，
   语义会割裂。改进方向是按标点+条款号做语义边界检测。
2. **向量每次重算**，无缓存。查询向量化是一次 DashScope 调用，
   高 QPS 下会成为瓶颈。改进方向是查询向量缓存（按 query 哈希）。
3. **`chatStream` 非真流式**：DashScope 侧未接 stream 接口，当前是整段生成后一次返回。
4. **评分门与改写依赖 LLM 输出格式**，正则解析失败按"不相关"处理，
   相当于静默丢弃该片段。改进方向是加重试或降级为纯 BM25 门控。
5. **审查完备性检查只覆盖 8 项固定要素**，未含知识产权归属、通知送达、
   不可抗力定义等实务中常见的缺失项；30% 违约金参照线取自司法惯例，
   不同地区与案情存在裁量空间。
6. **审查的法律依据未做支撑性校验**：检索命中的条款会作为依据展示，
   但未验证该条款是否真正支撑所给出的风险判断，存在引用相关但不精准的可能。
